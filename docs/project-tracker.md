## Phase 3 — Operational readiness (before paper trading)

### Error handling & recovery

- [x] API failure degradation behavior (skip / stale data / abort per data category) — documented in [`01-data-layer/api-failure-handling.md`](design/01-data-layer/api-failure-handling.md). Three-tier classification (Critical / Important / Optional) with aggressive fresh-or-abort semantics: no stale fallback for any category, abort means cancelling the entire pipeline invocation and waiting for the next scheduled trigger. Q4 short selling, Qual 2 social sentiment, and Qual 3 prediction markets are Optional (skip-and-log on failure) because their absence doesn't materially degrade decision quality; Q8 commodities is unconditionally Critical to avoid coupling the data layer to downstream candidate-selection logic. Continuous monitor retains independent safety authority during data-layer aborts except when Q1 live quote feed itself fails (a physical consequence of shared upstream dependency, not a design choice)
- [x] LLM agent failure handling (timeout, malformed output, context overflow) — documented in [`llm-agent-failure-handling.md`](design/llm-agent-failure-handling.md). Same fail-closed principle as the API failure spec, applied uniformly: every LLM agent is treated as Critical, and any unrecoverable failure aborts the invocation. No Important/Optional tiers and no peer-recovery path between analyst and strategist — a partial portfolio view is the same degraded-decision pattern fail-closed exists to prevent. Five failure modes (timeout, malformed output, context overflow, model API error, tool-use error) with bounded retry shapes per mode. Schema validation is the primary structural check; malformed output gets one corrective same-context retry then aborts. Context overflow is a uniform hard failure — no input pruning, no loop interruption, since every agent's inputs are bounded by design. Continuous monitor authority is independent of pipeline aborts; emergency invocations apply the same fail-closed rule without relaxed validation
- [x] Mid-pipeline failure: partial result persistence and checkpoint/resume strategy — documented in [`mid-pipeline-failure-handling.md`](design/mid-pipeline-failure-handling.md). Policy: no checkpoint, no resume. When an invocation aborts partway through (LLM agent failure, data-layer abort, infrastructure error), the pipeline process discards in-flight state and waits for the next scheduled trigger. Successful partial outputs are persisted as diagnostic records only, never replayed. Three reasons: fresh context windows are a core design principle; briefs decay fast at the 4–72h horizon (same no-stale-fallback rule as the data layer); the continuous monitor covers safety between invocations so no pipeline-side resume path is needed. Execution layer invariants preserved: collect phase is atomic, submitted commands remain committed (individually idempotent per forthcoming OMS idempotency spec)
- [x] Idempotency guarantees for OMS commands — scope landed across two docs after pressure-testing showed conventional dedup patterns don't fit the in-process, atomic-transaction, fail-closed architecture.
