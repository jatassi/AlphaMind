# Risk guardrails

Hard-coded programmatic constraints that prevent the system from taking on excessive risk, regardless of how compelling the thesis or how confident the LLM agents are. These are not LLM-mediated — they are deterministic rules enforced by code.

*Design principle — progressive validation, not single checkpoint:* Guardrails are not solely an execution-layer concern. A trade that violates a position size limit should be caught *before* the portfolio manager spends tokens evaluating it, not after. The guardrail system operates at multiple layers of the pipeline, with each layer applying the subset of rules relevant to its context. This prevents wasted computation and ensures that constraint violations surface as early as possible.

---

## Multi-layer enforcement model

Guardrails are checked at four points in the pipeline, progressively narrowing the set of valid actions. The first three correspond to the [decision layer](../04-decision-layer/README.md) architecture; the fourth is the engine backstop. See [rules-and-limits.md](rules-and-limits.md) for the per-rule mapping to enforcement tiers.

| Tier | Layer | Agent(s) | Guardrail role | Enforcement style |
|------|-------|----------|----------------|-------------------|
| T1 | Recommendation | [Analyst](../04-decision-layer/analyst.md) + [Strategist](../04-decision-layer/strategist.md) | Both agents receive guardrail headroom in their guardrail state headers and self-constrain during proposal generation. Before finalizing, each agent calls a shared **guardrail validation tool** that deterministically checks every proposal against all applicable rules — including delta-adjusted exposure for options — and revises proposals that fail. The tool tracks cumulative impact across multiple proposals within a single agent invocation. | **Advisory.** The agents are expected to produce guardrail-compliant proposals, but are not the enforcement authority. Violations that slip through are caught downstream. |
| — | Cross-agent annotation | [Proposal pre-processor](../04-decision-layer/proposal-pre-processor.md) | Deterministic computation between analyst/strategist outputs and the PM. Detects cumulative breaches that arise from the combined set of individually-compliant proposals across both agents — e.g., the analyst's proposals are compliant and the strategist's ADD recommendations are compliant, but together they breach a sector limit. Also computes capital requirements, same-underlying conflicts, and sector exposure shifts. | **Informational.** The pre-processor never blocks, filters, or modifies proposals — it only adds annotations. The PM uses these annotations to resolve cross-proposal interactions. |
| T2 | Approval | [Portfolio manager](../04-decision-layer/portfolio-manager.md) | The PM receives the pre-processor's annotated package alongside guardrail headroom. When the PM modifies parameters (sizing changes, instrument substitutions), it validates those modifications via the same guardrail validation tool. The PM makes sizing tradeoffs informed by headroom — e.g., approving a slightly larger position in a sector with room by sizing down elsewhere — but cannot override engine-authoritative limits. | **Judgment-informed.** The PM sees guardrail state alongside thesis quality and portfolio coherence. It can make nuanced tradeoffs that the agents' individual validation can't, but is not the final enforcement authority. |
| T3 | Execution | Engine guardrail layer | Final programmatic check before orders reach the execution gateway — the hard stop that rejects any command violating a constraint, regardless of upstream approvals. Because portfolio state can shift between T1/T2 validation and command execution (market movement, fill resolution, regime changes), this check is the authoritative backstop. Rejections are returned **synchronously** to the PM within the same invocation, allowing the PM to adjust and retry. | **Authoritative.** Deterministic, no override, no exceptions. If the PM approves something that violates a constraint due to stale state, LLM error, or race condition, the engine catches it. |

The execution layer is the **single source of truth** for constraint enforcement. The upstream layers (T1, pre-processor, T2) are optimizations — they reduce wasted work by catching violations early and providing the PM with pre-computed constraint context — but they are not relied upon for correctness. The system is safe even if all upstream layers fail to check constraints, because the engine layer is deterministic and comprehensive.

Between pipeline invocations, the **[continuous monitor](../05-execution-layer/architecture.md#4-continuous-monitor)** — a first-class system component that runs persistently during market hours — performs breach detection against live market data for rules that can be breached by market movement. When a breach is detected, the monitor may issue protective CLOSE commands via engine-originated [command envelopes](../04-decision-layer/portfolio-manager.md), depending on the per-rule classification in [breach-behavior.md](breach-behavior.md). The monitor can also trigger **emergency pipeline invocations** when market conditions deteriorate beyond what mechanical between-invocation actions can handle (see [breach-behavior.md](breach-behavior.md#emergency-invocation-trigger)). The continuous monitor has authority to close positions and trigger invocations, but never to open, add, adjust, or cancel — all constructive actions require PM judgment.

## Relationship to other specs

| Spec | Relationship |
|------|-------------|
| [Execution layer](../05-execution-layer/architecture.md) | The engine's guardrail enforcement layer (component 3) implements the T3 authoritative check. The [continuous monitor](../05-execution-layer/architecture.md#4-continuous-monitor) (component 4) implements between-invocation breach detection, protective CLOSE authority, and emergency invocation triggering. The enforcement *interface* is defined in the engine spec; the *rules* are defined here |
| [Analyst](../04-decision-layer/analyst.md) | T1 consumer. Receives guardrail headroom as context, self-constrains during proposal generation, validates each proposal via the shared guardrail validation tool before finalization |
| [Strategist](../04-decision-layer/strategist.md) | T1 consumer. Same guardrail validation workflow as the analyst, applied to position action recommendations (ADD, CLOSE, REDUCE). Receives position-level constraint proximity in its guardrail state header |
| [Proposal pre-processor](../04-decision-layer/proposal-pre-processor.md) | Cross-agent annotation layer between T1 and T2. Computes cumulative exposure impact across the combined analyst + strategist proposal set, detecting breaches that individual agent validation can't catch |
| [Portfolio manager](../04-decision-layer/portfolio-manager.md) | T2 consumer. Receives pre-processor annotations alongside guardrail headroom. Validates its own sizing modifications via the guardrail validation tool. Receives synchronous T3 rejection feedback from the engine and can adjust within the same invocation |
| [Portfolio state / raw state](../01-data-layer/internal/portfolio-state.md) | Category 4c (risk budget consumption) and 4d (active risk parameter set) are the read interface for guardrail state. Defined in portfolio state, sourced from this system |
| [Programmatic distillation](../02-distillation-layer/external.md) | Volatility regime classification (section 4) is the input to regime-dependent guardrail parameters. Funding stress and liquidity scores drive the stress overlay |
