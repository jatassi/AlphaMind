1Calibration

AlphaMind is an autonomous LLM-powered swing-trading system: a scheduled batch pipeline (data collection → distillation → analysis → decision → execution) plus a continuous-monitor sidecar, two processes sharing a SQLite database. By app-shapes.md's taxonomy it is a hybrid of K3 (data pipeline), K4 (long-running daemon), and K5 (agentic / LLM) — nine LLM agents per invocation, LLM-API latency dominates wall-clock.

The toolchain reads as deliberate and modern: Python 3.13, mypy --strict with warn_unused_ignores, ruff with an unusually broad rule set (DTZ, ASYNC, TRY, PD, NPY, FURB, LOG, PTH, SIM, plus all the PLR complexity gates). Boundary hygiene is on the radar. pyproject.toml declares its dependencies cleanly with a feature/dev split. The test suite is parallelized via pytest-xdist. Static-analysis posture is among the strongest you'll see in a Python codebase.

The codebase claims a layered architecture matching the design tracker: Foundation → Data → Distillation → Analysis → Decision → Execution + Risk guardrails. The implementation realises this shape correctly — packages are organised by feature, not by Django-style "models / views / controllers" tiering. But the import graph tells a different story than the docs: four cycles, two of them spanning four+ subdivisions, with explicit workarounds (lazy __getattr__, # noqa: E402, TYPE_CHECKING, function-local imports, re-export shims) keeping them runnable. Per P2 ("the import graph IS the architecture"), those workarounds are the architecture today. There is no import-linter configuration; layer rules are aspirational.

The audit's findings cluster on five themes: (1) cycles through shared types, (2) primitive obsession (zero Decimal in a money-handling system, bare str for IDs), (3) Pydantic as the default internal type instead of the boundary type, (4) functional-core leak in distillation (Session threaded into compute), (5) god modules at the OMS write boundary. All five are addressable; together they explain the workarounds, the test-fixture weight, and the friction reported in recent commits.

load-bearing P2 A2

L1 — No import-linter configuration; layer rules are aspirational

Where
No [importlinter] section in pyproject.toml; no .importlinter file. Confirmed by analyze_imports.py (import_linter_config.found = false).
Why it matters
P2: the import graph IS the architecture. The codebase has 539 modules across 15 declared layers; the layer names are encoded in package paths (config/ is boundary, persistence/ is adapter, pipeline/ is shell). But none of those rules are checked. The four cycles below slipped through code review precisely because nothing fails when a layer rule is broken. The workarounds in place (__getattr__ lazy-loaders, # noqa: E402 chains, TYPE_CHECKING imports) all exist because there was no friction at the moment the violation landed.
Fix
Add import-linter to dev dependencies. Start with two layered contracts (kernel-and-commands at the bottom, no imports across the four "vocabulary" layers) and the two cycle-prevention forbidden contracts (decision.* ↛ execution.*, portfolio_state.* ↛ risk_guardrails.*). Add to the existing pre-commit / CI checks alongside ruff and mypy. This is the gating finding: every cycle-fix below stays fixed only if this is in place.
load-bearing P2 P4 A2

L2 — 10-module cycle: portfolio_state ↔ risk_guardrails ↔ distillation ↔ persistence

Where
portfolio_state.aggregates.drawdown → portfolio_state.aggregates.risk_parameters → risk_guardrails.breach_behavior.types → portfolio_state.records.capital → distillation.baselines → distillation.regime → risk_guardrails.regime_adaptation.types → persistence.models → distillation.calibration → distillation.output → (back to drawdown).
Why it matters
P2 + P4 inversion. Three concrete root causes (the audit subagents converged on this independently):
  1. Four shared enums live in risk_guardrails but are needed by every layer: RegimeLabel, RegimeTransitionState, RiskZone, DrawdownTier. portfolio_state.aggregates.{drawdown,risk_parameters} import them upward.
  2. persistence/models.py:25 imports CALIBRATION_STATE_VALUES (three string literals) from distillation.calibration.py:47-51 — persistence (a boundary layer) reaching up into distillation for vocabulary.
  3. portfolio_state/records/capital.py is a 50-line re-export shim whose docstring admits ALP-344/ALP-347 status: "Identity is preserved across all import paths." It's the cycle's main wire — it lets risk_guardrails import "from portfolio_state" symbols that live in risk_guardrails.
The workarounds in place — # noqa: E402 chain at regime_adaptation/types.py:62-66, TYPE_CHECKING imports, function-local lazy imports in distillation/calibration.py:216,303 — make the cycle runnable, not fixed. Every consumer's tests drag in the entire cycle to construct one DrawdownState.
Fix
Extract a leaf module src/alphamind/_kernel/ with zero first-party deps:
  • _kernel/regime.py — RegimeLabel, RegimeTransitionState, RiskZone, DrawdownTier
  • _kernel/calibration.py — CalibrationState, CALIBRATION_STATE_VALUES, EXTENDED_HOURS_BOOTSTRAP_RATE
Then: every subdivision imports from _kernel; delete portfolio_state/records/capital.py (or repurpose as one-line shim → _kernel); remove the # noqa: E402 chain; remove the lazy imports in distillation/calibration.py. Add the corresponding import-linter contract from L1.
load-bearing P2 P4

L3 — 12-module cycle: decision.portfolio_manager ↔ execution (acknowledged in code as "transitional")

Where
Decision → Execution (5 edges): decision/portfolio_manager/models.py:34 (OMSCommand family), validation.py:49, harness.py:52,57, runner.py:48.
Execution → Decision (3 edges): execution/oms/submit_envelope_mcp.py:49-53, oms/command_ids.py:23 (TYPE_CHECKING), state_persistence/write_paths/phase2.py:22-23.
Why it matters
P4 — the envelope is owned in the wrong place. Decision produces command envelopes; execution consumes them. The natural direction is decision → execution. But command_models.py lives in execution, PMEnvelope wraps OMSCommand as a discriminated union, so decision must depend on execution to define its own output. The submit_envelope MCP wrapper in execution then validates PMEnvelope, forcing the reverse edge. Cycle closes.

The code knows. oms/__init__.py:28-32 docstring: "submit_envelope_mcp symbols are loaded lazily via __getattr__ so that alphamind.decision.portfolio_manager.models's import of canonical OMS command types does not create a circular import." oms/__init__.py:143-173 is a 30-line custom __getattr__ implementation. submit_envelope_mcp.py:1 docstring: "transitional ... until the real OMS submission engine lands in ALP-120." The workaround has shipped to main, but no follow-up is filed and no import-linter rule prevents the next code-path from extending it.
Fix
Two motions, can land as one PR (no behavior change, ~30-40 files touched):
  1. Move OMS wire types to a kernel. Promote oms/command_models.py and oms/engine_envelope.py to a new top-level src/alphamind/commands/ package. Both decision and execution depend down on commands.*.
  2. Invert submit_envelope_mcp via a Protocol. Move the engine-stub next to its caller — decision/portfolio_manager/submit_envelope.py. Define BrokerDispatch(Protocol) in commands/protocols.py; execution implements it; PM resolves via DI at the composition root.
The __getattr__ lazy-loader disappears; oms/__init__.py shrinks to a normal re-export.
load-bearing P3 D2

L4 — Primitive obsession: zero Decimal, zero NewType IDs in a money-handling system

Where
Zero Decimal uses anywhere in src/alphamind/. 115 L12 findings of : float for monetary fields. Zero NewType aliases for IDs. Hot spots:
  • portfolio_state/events/activity_log.py (16 money fields including fill_price, exit_price, realized_pnl_usd, fees, amount_usd, margin_required_usd, loss_usd)
  • execution/state_persistence/write_paths/phase2.py:1313-1359 — cash_row.reserved_capital_usd = cash_row.reserved_capital_usd + amount_usd is the buying-power source of truth, with float drift (:1349's max(... - ..., 0.0) patch is the tell)
  • decision/{analyst,strategist,portfolio_manager}/models.py — 17 float annotations for prices/dollars flowing analyst → strategist → PM → execution; the full LLM-emitted command envelope never sees Decimal
  • IDs: OrderId, PositionId, BracketId, CommandId, AlpacaOrderId, ClientOrderId, InvocationId, EnvelopeId, ThesisId — all bare str with regex validation at the Pydantic boundary and bare str internally
Why it matters
P3 + D2. This is a system that places real money trades. Float arithmetic accumulates binary-rounding error: 0.1 + 0.2 == 0.30000000000000004; seven adds of 0.1 return 0.7000000000000001. The activity log records every fill, debit, credit, margin call, dividend — equality across event types and persistence round-trips will diverge over time. Buying-power math compounds the drift on the source of truth. Pricing precision questions may be deferred intentionally (Alpaca accepts floats, broker round-trips truncate), but the absence of any commentary about that decision is itself a finding — no Decimal in 133K LOC of trading code is a one-way door that's been quietly walked through.

For IDs: the type checker cannot catch submit_equity_close(symbol=position_id, ...). Two ticker strings (underlying vs OCC vs broker symbol) collapse to str. Regex validation runs at the Pydantic boundary; internal call sites trust bare str and re-validate or pray.
Fix
In _kernel/money.py and _kernel/ids.py: 
from decimal import Decimal
from typing import NewType

Money = NewType("Money", Decimal)
Price = NewType("Price", Decimal)

OrderId = NewType("OrderId", str)
PositionId = NewType("PositionId", str)
BracketId = NewType("BracketId", str)
CommandId = NewType("CommandId", str)
EnvelopeId = NewType("EnvelopeId", str)
Symbol = NewType("Symbol", str)
OccSymbol = NewType("OccSymbol", str)
InvocationId = NewType("InvocationId", str)
ThesisId = NewType("ThesisId", str)
Migrate _usd floats to Money at the boundary types first (TradeAccountSnapshot.cash, FillRecord.fill_price, command-model dollar_value/trigger_price). The Alpaca SDK returns strings for monetary fields — parse once at the boundary, internal code is correct. Plan as a coordinated migration with the activity-log codec layer; this is the largest single change in the audit.
load-bearing P5 D1

L5 — Pydantic for internal types: 180+ violations across every subdivision

Where
The L9 scanner reported 363 findings system-wide; per-subdivision triage shows ~180 are real P5 violations (the rest are warranted boundary usage). Hot files:
  • portfolio_state/events/activity_log.py — 45 BaseModel internal-event detail classes (1033 LOC total)
  • portfolio_state/{records,aggregates,consumers}/* — 71 more (orders/positions/theses/aggregates)
  • analysis/{domain_researchers,qualitative_research,adaptive_research,synthesizer}/{runner,harness,validation}.py — 31 HarnessSuccess, runner results, validation results
  • decision/{analyst,strategist,portfolio_manager}/{validation,runner,harness}.py — 15 (Validation*, *Result, HarnessSuccess)
  • execution/{oms,continuous_monitor,state_persistence} — ~15 in Group C internal (Monitor session, command-id components, invocation records)
  • risk_guardrails/state_delivery/portfolio_manager.py — 5 (renderer parameter bags)
  • scheduler/session.py:19-26 — PipelineSession
Why it matters
P5: Pydantic at trust boundaries; frozen dataclasses internally. Internal carriers pay full Pydantic validation cost on every construction (per-field iteration, validator dispatch, error context), lose __slots__, and signal "this could carry untrusted data" to readers who then add redundant defensive checks. Boundary usage is correct in many places — LLM tool I/O, vendor JSON ingest, config YAML, persistence codec inputs — but the discipline doesn't propagate inward. The activity_log.py case is the densest: 38 nearly-identical 6-field detail classes that exist only to record state to SQLite, with validators (_validate_timestamp_tz_aware, _validate_event_group) that are post-construction invariants — exactly what frozen dataclass + __post_init__ expresses with zero Pydantic machinery.
Fix
Convert internal types to @dataclass(frozen=True, slots=True) with __post_init__ invariants. Keep Pydantic only on: LLM tool I/O, brief schemas, vendor-JSON parsers, config models that get hot-reloaded, and on-disk manifest contracts (e.g. replay_harness/fixtures.py:46 SliceManifest). Order the migration leaf-first: convert one record (e.g. UnsettledProceedsEntry), let mypy --strict verify the 30+ call sites still type-check, then proceed upward.

L6 — Functional-core violation in distillation/: Session threaded into compute path

Where
99 session.* calls across 22 of 54 distillation files. distillation/q1/assemble.py:1103,1156,1176,1247; distillation/q6_macro.py:393,440,539,596,817; distillation/q3/assemble.py:188+; distillation/q7/_helpers.py; distillation/qualitative_derived.py:165,208,250,450,480,676,700,741. Counter-examples that prove the seam works: distillation/normalization.py (341 LOC pure, 10 exports, zero DB) and distillation/q1/indicators.py (636 LOC pure).
Why it matters
P1: functional core, imperative shell. Distillation's docstrings claim "deterministic numerical computation," but the call shape interleaves DB reads with arithmetic. _assemble_blocks_for_audience at q1/assemble.py:1176 issues an N+1 _load_daily_bars per ticker; _build_indicator_group_blocks at line 1247 calls _compute_gap_per_ticker(session, ...) which re-enters the DB inside what callers reasonably read as a "compute" pass.

The cost has surfaced. distillation/orchestrator.py:706-769 is forced to serialize all six categories with a code comment: "running them concurrently via asyncio.to_thread on a shared Session triggers Session is already flushing." The shared mutable session is forcing sequential execution that the orchestrator's own design intended to be parallel. Tests also pay: tests/distillation/external/test_orchestrator.py:76 spins up sqlite:///:memory: for unit tests that should only need lists of bars; test_q3_assemble_blocks.py:67-225 runs _seed_universe → session.add → session.flush per case.
Fix
Split each assemble_q*_blocks(session, ...) into:
  • load_q*_inputs(session, ...) -> FrozenInputs — thin shell, all reads in one pass
  • compute_q*_blocks(inputs: FrozenInputs, config) -> list[OutputBlock] — pure core
Phase 2 of the orchestrator becomes: load shells sequentially under one session → drain to frozen dataclasses → asyncio.gather(*[asyncio.to_thread(compute_*)...]) with no shared mutable state. Reuse the existing _IndicatorGroupContext (q1/assemble.py:1229) — it's already the right shape for the input bundle. Pilot on q1/gap.py and q1/anomalies.py (smallest blast radius), then propagate.
load-bearing P5 D2

L7 — Pydantic config types leak system-wide into domain code

Where
config/models/*.py declares 61 Pydantic BaseModel config classes. They're imported directly by 65+ files across distillation/, analysis/, decision/, risk_guardrails/, execution/. Example: distillation/q1/assemble.py:42,1035,1106,1179 takes config: DistillationConfig (Pydantic) as a parameter; pipeline/_shared.py:54 does cfg.model_copy(update=...) on Pydantic config models.
Why it matters
P5. The pattern exists in design: config/resolver.py:83 defines ResolvedConfig as a @dataclass(frozen=True, slots=True). The intent is parse-once-at-boundary. But the per-domain Pydantic models pass through ResolvedConfig directly (config/resolver.py:99-120), so business code calls .model_copy() and depends on Pydantic-specific validation semantics. The config/models/__init__.py 277-line file re-exports 119 symbols — it is the de facto boundary registry and the vehicle for the leak.
Fix
Per top-level Pydantic config the analysis/decision/distillation layers import, define a frozen-dataclass mirror in the consuming package and convert via a single to_domain() function. Start with DistillationConfig (235 LOC, 10 leaks) — highest yield since it's duck-typed across the distillation Q-modules. Once each domain config has a converted-once internal type, the 119-symbol re-export registry in config/models/__init__.py shrinks to just the resolver/snapshot symbols.

Where

Orchestrator drops to ~600 LOC.
  • LLM harnesses — extract analysis/_harness_core.py with the SDK driver loop, prompt cache, exception hierarchy, _DiagState writer. Variants become a small Protocol: parse_response(payload, response_text) -> T | RetryRequest, build_options(agent_config, ...) -> ClaudeAgentOptions.

L9 — SQLAlchemy ORM models are imported as system-wide vocabulary

Where
persistence/models.py — 1040 LOC, 31 declarative classes, no __all__ — imported by 93 first-party modules. persistence/__init__.py is 0 bytes. pipeline/analysis.py:32,110 passes Session directly to run_analysis_pipeline. Many data_sources modules construct ORM rows inline: polygon/equity.py, finnhub/calendar.py, etc.
Why it matters
P2 + P4. The ORM declarative classes (a boundary type) are the system's domain vocabulary. There is exactly one Protocol-style repository in the codebase — portfolio_state/repository.py (PortfolioStateRepository Protocol + StubPortfolioStateRepository) — and it works well. Nothing else has equivalent seams. The cost surfaces in tests (P8: every read-path is mock-the-session or hit-real-DB, not sociable testing against a Protocol fake) and in coupling (an ORM column rename touches 93 modules).
Fix
Per subsystem with non-trivial domain rules, introduce a Protocol-shaped repository in the consuming package (template: portfolio_state.PortfolioStateRepository) and an SQL implementation that closes over the session. Don't touch analysis tools that are pure read-throughs of one table — they're fine as functions; the win is concentrated on multi-table aggregating reads. Add __all__ to persistence/models.py; populate persistence/__init__.py with the published surface. Add an import-linter contract banning direct ORM imports outside persistence/ and the SQL-implementation modules. This is a multi-quarter migration done one consumer at a time.
load-bearing P7 G2

L10 — Async surface over synchronous core: structured concurrency violations

Where
Three related sub-findings:
  • Repository Protocol async over sync SQLite. portfolio_state/repository.py:133-190 declares 19 async methods; the Stub at :232-305 defines 19 async def with no await anywhere. Same pattern in consumers/synthesizer.py:73-81 Protocol + :193-210 SnapshotBackedSynthesizerReader; pricing.py:43-113. The 14-concurrent asyncio.gather in assembler.py:449-468 is decorative — SQLite's single-writer pool serializes them.
  • asyncio.gather instead of TaskGroup for parallel agent execution. analysis/domain_researchers/orchestrator.py:115 (3 sector researchers fan-out), pipeline/analysis.py:148 (orchestrator || qualitative). asyncio.gather(return_exceptions=False) propagates the first exception but cancellation of siblings is best-effort.
  • asyncio.create_task without TaskGroup parent. Five sites: scheduler/supervisor.py:101, execution/continuous_monitor/supervisor.py:108, execution/broker_adapter/fill_stream.py:324, execution/continuous_monitor/underlying_stream/task.py:243,244. scheduler/supervisor.py is a hand-rolled ~190-LOC supervisor pre-dating TaskGroup adoption.
Why it matters
P7. Glyph: "async is not for you." Async earns its keep when there are concurrent I/O operations. SQLite is the persistence engine — synchronous, serialized. The async colour spreads through every consumer (every test must pytest.mark.anyio, every site spins an event loop) for no benefit. Separately, structured concurrency (TaskGroup) is mandatory once async (Nathaniel J. Smith): fire-and-forget create_task is a guaranteed silent bug. Python 3.13 has TaskGroup; the hand-rolled supervisor is ~150 lines of cancellation logic TaskGroup provides for free.
Fix
  • portfolio_state repository: strip async from the Protocol + Stub + snapshot reader + pricing provider. assemble_snapshot becomes sync. 14-concurrent gather collapses to 14 sequential reads (already what happens). Right answer if SQLite stays.
  • analysis parallel execution: replace the two asyncio.gather(...) with async with asyncio.TaskGroup() as tg: blocks; collect from tg.create_task(...) handles. Fail-closed semantic preserved; multi-failure raises ExceptionGroup.
  • scheduler/continuous_monitor supervisors: replace hand-rolled supervisor with TaskGroup-based ~80-LOC supervisor. The except BaseException: at supervisor.py:127 and the _RegisteredTask mutable-dataclass disappear.

9What looked good

The audit found enough structural problems to fill ten load-bearing findings, but the codebase also gets several things right in ways that are not common at this scale. These are worth preserving through any refactor.

  • Static-analysis posture from day one. mypy --strict with warn_unused_ignores; ruff with DTZ, ASYNC, TRY, PD, NPY, FURB, LOG, PTH, SIM, and the PLR complexity gates. Per-file ignores are itemized and justified in pyproject.toml. This is the strongest static-analysis posture you typically see in a Python codebase.
  • Test-to-code ratio 1.6:1 (211,710 LOC tests vs 133,056 LOC src). Tests organized by feature mirroring src/. The discipline is real, even though the substrate is mock-heavy in data_sources (see L9 / W3 fixes).
  • distillation/computations/ + distillation/normalization.py are exemplary P1. normalization.py is 341 LOC pure, 10 exports, zero DB. q1/indicators.py is 636 LOC pure. q3/pair_trade.py is import-free pure math. These prove the project can write functional-core code; the contamination in L6 is structural to the assemble/baseline triple, not universal.
  • risk_guardrails/guardrail_evaluation/rules/ is reference functional-core code. Pure rule evaluators taking frozen-dataclass inputs and returning float; no I/O, no clocks, no randomness. RuleSpec is a well-typed frozen dataclass with explicit Callable[..., float] — uniform plugin interface done right. The ARG001 suppression in pyproject.toml is the correct tradeoff for this pattern.
  • execution/oms/command_models.py applies P3 cleanly at the boundary. Direction, EntryOrderType, TargetType, LegType, Comparator, CloseRationaleType, StrategyType, ContractType are all Literal; instrument variants use Annotated[..., Discriminator("asset_type")]; per-leg invariants via model_validator(mode="after"). 11Open questions

  • Is float for prices intentional, or has the deferral leaked? The audit found zero Decimal in 133K LOC and no marker comment explaining why. Broker round-trips probably truncate to 4 places anyway, and on whole-share equity at 60-80 tickers the per-trade cents drift is small — but the buying-power accumulator at phase2.py:1313-1359 grows over time. If float is deliberate (e.g., "broker accepts strings, drift is bounded by daily reconciliation"), L4's fix becomes narrower: Money only in the activity log and the cash ledger; not in command envelopes. Worth a five-line decision doc.
  • Should the four shared enums (RegimeLabel, RegimeTransitionState, RiskZone, DrawdownTier) live in _kernel/regime.py or in config/models/guardrails.py? The audit recommends a new top-level _kernel/, but if config/models/guardrails.py is already a leaf in the import graph, folding the enums there has zero new files and the same cycle-breaking effect. Check the actual import graph of guardrails.py before committing to a new package.
  • Is portfolio_state/repository.py's async surface a deliberate forward-compat hook for a future Postgres migration? If yes, L10's recommendation flips: keep the async colour and add # justified-async markers on each Stub method. If no (SQLite is the foreseeable future), strip it. The references/data-and-state.md doc says "If the system ever needs multiple machines or higher write concurrency, PostgreSQL is the natural migration — connection-string change plus minor dialect adjustments, not a rewrite," which sounds like the latter: a future migration, not an immediate one. Confirm.
  • Should portfolio_state.consumers/ live next to the portfolio_state package, or next to its consumers in decision/ and risk_guardrails/? Today, portfolio_state/consumers/portfolio_manager.py is imported by 7 modules outside portfolio_state (decision PM runners, risk_guardrails state_delivery, scripts). The package boundary suggests consumers are portfolio_state-internal; the import pattern suggests they are consumer-internal. Per Cosmic Python's "where Protocols live" convention (with the consumer, not with the producer), moving them next to callers is the principled answer — but that's a system-wide rename. Worth a conversation, not an immediate fix.
